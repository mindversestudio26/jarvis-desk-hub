# JANGE backend operations — isolated prototype

The product name is JANGE (जङ्गे). Repository, technical identifiers, cookie names, API paths and database names remain unchanged. This document does not authorize hosting changes. Keep PR #1 Draft and staging's 403 gate intact.

## Workspace and schema transition

Fresh initialization generates independent random 128-bit `subject_id`, `workspace_id` and `generation` fields on the owner row. Subject/workspace never change during ordinary edits or password rotation. Generation is separate from numeric revisions. All mutations carry the full binding; the owner transaction lock protects session revalidation, binding verification, retry lookup, revision check and commit. A missing binding is 428; a different binding is 412, including already-seen operation IDs. No implicit compatibility bypass exists for older clients.

Existing schema installations are NOT automatically ALTERed. Existing staging currently has the earlier empty schema: do not run new init over it and assume migration occurred. Before any approved hosted migration, export/verify the old schema, prove the owner/records state, prepare an independent empty v2 target with the new schema, and restore/verify it. No DROP, conversion or live-host migration has been run. Format-1 encrypted archives remain supported by the local restore drill and receive new identity metadata; format-2 preserves subject/workspace. Both generate a fresh generation and omit sessions. Old unbound client data needs explicit export/archive and review, never automatic replay.

Database replacement/restore/key rotation must use the reviewed restore procedure. Swapping a physical database clone without rotating generation could copy its identity and defeat this protection; identifiers cannot detect an administrator copying all metadata verbatim. Never restore a raw snapshot directly into a live endpoint. Close the gate, revoke old sessions, restore into an empty isolated target, generate fresh generation, verify it differs, and then seek release approval. No restore endpoint exists.

## Multi-tab and offline contract

The backend adapter changes only its own IndexedDB cache, never dashboard localStorage or Claude UI. Every enqueue/acknowledgement/conflict decision reads fresh state inside a single readwrite transaction. IndexedDB serializes these across tabs; BroadcastChannel is an optional invalidation hint, not a lock. No Web Locks dependency. Network calls stay outside IDB transactions to avoid Safari auto-close problems. Cached records merge only nondecreasing revisions, including tombstones. Server operation IDs ensure a committed request whose acknowledgement was lost cannot be applied twice. Two tabs may transmit the same operation safely; no fragile browser leader lease is required.

Each queue operation stores its immutable binding. A mismatch blocks synchronization without overwriting cached records/drafts. A truly empty cache may bind on authenticated first sync. An unbound legacy cache with any records, pending edits or conflicts cannot. `exportLocal()` returns active and quarantined workspaces for an explicit private export. `switchWorkspace(expectedBinding)` requires a freshly read matching target binding; callers must display both identities/generations and obtain an explicit choice. It atomically archives the entire former cache and starts an empty active workspace. No automatic relabeling, cross-generation "keep mine", or archive deletion exists. Claude must add the reviewed handoff UX separately; no visual changes were made here.

A durable cache epoch prevents late responses from restoring cached data after another tab logs out or switches workspace. Logout rejects pre-existing drafts; if another tab queues a draft during logout, the server session is revoked and the draft is retained with an explicit error rather than erased. The adapter never assumes revocation erases data already downloaded to another device. Trusted-device offline content remains readable in browser storage; use an OS passcode. Browser eviction/storage loss and tab termination cannot be prevented; the adapter acknowledges saves only after IDB commits, exposes export and reports storage errors. iPad foreground/resume synchronization remains necessary.

## Password administration and recovery

`bin/admin.php` is CLI-only and currently refuses every non-local/non-SQLite target. No public reset route, recovery backdoor or emailed token exists. Rotation takes `JARVIS_CURRENT_PASSWORD`, `JARVIS_NEW_PASSWORD` and exact `JARVIS_ADMIN_WORKSPACE` through a private environment. Recovery requires controlled machine/database access, the exact workspace ID and explicit `JARVIS_ADMIN_CONFIRM=LOCAL-RECOVERY-REVOKE-ALL`. That confirmation is not a secret or a substitute for OS/database access. Both actions atomically update bcrypt and revoke ALL sessions. A login that verified the old hash before rotation must recheck that hash under the owner lock before creating a session.

For real lost access, first retain the deny-all gate, verify owner authority using an independent channel, preserve an encrypted backup and key, check the exact workspace, and use an independently reviewed host CLI procedure. Hostinger SSH is inactive; do not activate it or install a public administration script as a workaround. Credential entry is an owner handoff. The local tool is not a certified Hostinger recovery mechanism. Changing the password cannot recover a lost data-encryption key.

## Encryption-key rotation and backup recovery

`bin/backup.php export <private-new-path>` takes an atomic owner/records/operations snapshot and writes an authenticated encrypted archive using exclusive creation, bounded at 128 MiB. Preserve the old key separately from the archive. Do not put either in Git, chat or public directories.

The isolated `restore-local` command supports optional `JARVIS_BACKUP_DATA_KEY` (old archive key), while `JARVIS_DATA_KEY` is the new target key. It authenticates the archive and every record/retry payload before insertion, re-encrypts all ciphertext when keys differ, rotates generation, and restores into an empty local SQLite or strict loopback disposable MariaDB target only. The source and old archive remain unchanged. Old keys cannot decrypt the new target; old backups still require old keys. This copy-and-verify drill avoids an unsafe in-place key/config cutover. The MySQL local drill accepts only the exact loopback DSN and jarvis_test_<hex> database namespace; hosted/production restore remains disabled. No production key rotation, keyring or automatic deletion of old keys is enabled.

Before real cutover, verify row counts, Unicode/live/deleted records, revisions, operation history, owner identity, fresh generation, excluded sessions, old-key rejection and source invariance; keep an offline rollback release/config and encrypted archive. Do not switch until independently reviewed. Rollback also needs a fresh generation: rolling back old files/database identity unchanged can accept stale queues. Key loss without a separately protected copy is unrecoverable; encryption is server-side, not E2EE.

## Retention, grants and logs

Runtime DB identity must have only SELECT/INSERT/UPDATE/DELETE on the dedicated application database; migration/restore credentials must be separate. Do not grant global, GRANT OPTION, FILE, PROCESS, CREATE, ALTER or DROP to runtime. Check effective privileges and connection identity privately, including inherited roles; sanitize output before sharing. The current Hostinger migration credential previously had broad database-scoped DDL rights, and no restricted runtime credential has been verified. No credential/grant changes were performed.

Policy for the prototype: expired session rows may be removed after absolute/idle expiry; login bucket metadata older than 24h is removed during login. Active sessions never survive password changes or restores. Records, tombstones and operation history are NOT automatically pruned: arbitrary pruning could resurrect offline deletions or allow duplicate retries. Current caps (1000 retained records, 5 MiB, 10000 operations) fail closed pending reviewed maintenance. A future compaction must close writes, create an encrypted snapshot, rotate generation and require explicit client reconciliation. A delete hides current content but is not permanent erasure of retry history/backups.

Proposed operational retention, not an installed Hostinger job: minimal fixed-event security logs 14 days, encrypted staging backups 7 daily copies plus pre-migration copy, owner review before deleting any archive/key. Confirm recovery needs before adopting a production retention policy. Private log directory 0700/files 0600, no payload/cookie/password/IP logging, size cap/rotation and disk alerts must be verified before deployment. Hostinger diagnostic log_errors was Off; no shared PHP option or cron was changed. Current code emits only fixed event/status/time metadata; private logging/rotation and retention enforcement remain deployment gates. Never expose an error_log file in public_html.

## Long-lived sessions, MFA and passkeys — proposal only

Current 12-hour absolute / 30-minute idle sessions remain unchanged. Do not make the main bearer cookie effectively permanent. A future opt-in trusted-device design can combine short access sessions with a separately hashed, rotating, host-only Secure/HttpOnly/SameSite refresh cookie, per-device token family, atomic single-use rotation and reuse detection. Propose an absolute 30-day device lifetime and explicit revocation, with recent step-up authentication for password/key/permission changes. Multiple tabs need coordinated renewal and recovery from an uncertain rotation response; implement/test before adoption. Password reset/restore must revoke both access and refresh families. This proposal is not deployed or implemented.

Passkeys are feasible with HTTPS WebAuthn: random challenges with expiry and single use, strict RP ID/origin verification, registered credential public keys bound to immutable subject, and user verification required. Choose the final stable origin/RP boundary before enrollment; GitHub Pages and staging credentials do not automatically share identity. Use a maintained verifier instead of homemade CBOR/signature handling; audit free dependencies. Test physical iPad/iPhone/Mac/Windows authenticators and owner-controlled recovery first. TOTP is a fallback with encrypted seeds, narrow replay-safe time windows, rate limits and hashed single-use recovery codes; it is not phishing resistant like origin-bound passkeys. Neither MFA nor passkeys are implemented or marketed as active.

References: [OWASP sessions](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [W3C WebAuthn](https://www.w3.org/TR/webauthn-3/). The local system-design-primer ACID/consistency reference informed transaction boundaries; no code copied.

## Sodium decision

Dwi-reviewed Hostinger support now says extension settings apply per selected website and custom php.ini/FPM pools are unavailable on Business hosting. Other websites' settings/files are not expected to change, but exact worker restart/reload scope was not explicitly certified. No sodium activation or shared setting change was made. Obtain the missing effect statement and explicit owner approval before activation. Keep native sodium mandatory and staging denied.

The pinned sodium_compat v2.5.2 scratch review is outside the repository/runtime: ISC license, PHP 8.1+/64-bit requirement, opportunistic native use and no upstream claim of a formal independent cryptographic audit. A deterministic local XChaCha20-Poly1305 smoke matches native output and rejects tampering; it is not broad assurance. Before any adoption require provenance/version review, complete used-primitive/interoperability/negative vectors, nonce handling, representative PHP 8.3 CPU/memory limits and independent Hostinger support validation. Pure PHP performance can be much slower; never weaken crypto or silently fall back. No dependency was added and no hosted polyfill test was run.
