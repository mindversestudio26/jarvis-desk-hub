# Backend hardening / staging gate

This update changes backend behavior only. No dashboard/Claude assets, DNS, email, website, database or public service was changed. The existing 19 files were inspected; the visual console remains untouched.

## Correctness changes

- Retry of an already committed operation returns the latest canonical record, preventing a delayed retry from rolling a client view backwards. Reusing an operation ID for different content still returns 409.
- Snapshot records and revision are read under the same owner transaction lock.
- Mutations and revocation revalidate the authenticated session under the same lock. A write ordered before revocation may finish; a write ordered after revocation is rejected. Remote revocation cannot erase downloaded offline data.
- UUID validation now requires exact grouped hexadecimal shape.
- API rejections/internal failures generate structured PHP error-log events with fixed event name, status and UTC timestamp. No request payload, password, token, note or IP is logged. Hosting log permissions/rotation still require verification; these are diagnostic events, not a tamper-proof audit ledger.

## Claude API contract

Existing v1 routes and schemas in README remain compatible. POSTs require exact Origin, JSON, session cookie and X-CSRF-Token except login. Login returns csrf/session_id/expires. GET session refreshes CSRF. Cookies must never enter JS persistence. Sync writes carry stable operation_id, kind, id, base_revision, deleted, data. Retry identical payload after uncertain outcomes. Successful retries can return a record newer than the original operation. 409 retains the local draft and current record; do not silently overwrite or discard it. Snapshots include tombstones. Notes stay online-only. 401 requires login; 429 requires backoff; 503 retains queued edits. Device activity is browser activity only. Control remains denied; AI remains disconnected.

Do not repoint an origin to another database: immutable workspace binding and multi-tab queue coordination remain unresolved client-integration gates. The prototype adapter must not be treated as production-safe for simultaneous tabs. Do not deploy Claude integration before those are resolved and browser regressions are run.

## Staging installation (requires explicit approval)

1. Approve a specific separate staging hostname, separate document root and dedicated empty database. Do not use Glow With Imane public_html, its databases, mail or DNS records. Preserve existing hosting backups and manually verify their availability before any approved infrastructure change.
2. Keep release source, CLI tools, secrets and backups outside every public root. Point only the staging document root to backend-prototype/public. Never publish preflight.php, init.php, schema or state directories. Store environment configuration outside source control and outside public roots; confirm hosting-specific injection method without public diagnostic pages.
3. Use a migration-only administrator to create tables; explicitly verify all five tables are InnoDB and utf8mb4. Runtime account receives only SELECT, INSERT, UPDATE, DELETE on this dedicated database, never global/DDL/FILE privileges. Remove migration credentials after setup. This repository does not silently convert existing database engines or collations.
4. Run CLI `php bin/preflight.php` using the actual staging PHP 8.3 executable with configured environment. It is read-only, prints no DSN/key/password and makes no schema change. It confirms driver and table engines only, not full integration correctness.
5. Run API tests against a disposable staging fixture database only after adapting the SQLite-specific harness. Verify real concurrent requests/rollback, sodium roundtrip, HTTPS Secure/HttpOnly/Strict cookie behavior, CSRF, auth rejection, disabled controls, API cache bypass, log rotation, extension activation and quota behavior. Current test harness does NOT validate MySQL.
6. Export a consistent encrypted database backup using the host's approved backup facility, separately preserve the data key, restore into a second isolated database, compare decrypted synthetic records/revisions/tombstones and confirm old sessions are revoked before any cutover. CLI `php bin/backup.php export <private-new-file>` creates an authenticated encrypted logical archive, excluding sessions and rate buckets. `restore-local` is deliberately restricted to an empty loopback-development SQLite database; it rejects existing data, corrupt archives and archives over the shared 128 MiB bound. The local drill is tested. This does not certify Hostinger/MySQL restoration; production restoration remains disabled. Preserve the encryption key separately, restrict backup filesystem ACLs, and never publish archives. Never test restoration over the live database.
7. Rollback uses the previous release directory and unchanged database only if no incompatible migration occurred (none in this patch). Keep staging disabled until review. If restoring older data, quarantine offline queues and require reconciliation before writes: old revisions can collide with restored history. Do not claim automatic safe rollback of client queues.

## Evidence and exact blockers

Baseline: 18 API regressions passed on local PHP 8.5.10 + SQLite. Updated suite: 25 passing tests, including latest-state retry, expiry, revoked writes, encrypted local restore/tamper/overwrite checks and two independent PHP-process concurrent writes (one success, one conflict). Chromium and Windows WebKit backend browser suites passed; Chromium offline reload and queue replay passed. WebKit offline simulation and physical iPad Safari remain unverified. PHP lint and git diff checks passed. Static code review found an archive-size mismatch; export and restore now share the same bounded size limit. Actual Hostinger PHP 8.3 execution, MySQL/InnoDB integration, MySQL concurrent-request integration and Hostinger backup restoration have not been demonstrated. No local mysql/mariadb/docker executable was found. No staging activation is authorized. PHP syntax compatibility by inspection is not execution on PHP 8.3.

Read-only hPanel PHP 8.3 selection and extension listing were rechecked on 2026-10-16 without saving changes. Other previously observed hPanel evidence: Business hosting; PHP 8.3 selected; PDO MySQL/sodium listed but activation unconfirmed; 2 CPU, 3 GiB RAM, 60 PHP workers, 120 processes; daily backups; managed SSL active. These observations do not prove runtime modules, effective quotas, successful restore or authenticated HTTPS API behavior. No new hosting runtime probe was published.

Still blocked before production: immutable workspace/restore generation binding, multi-tab durable queue coordination, actual MySQL transaction tests, Hostinger/MySQL backup/restore drill, key rotation and recovery design, audit retention/access review, host HTTPS/CDN checks, independent security review. Existing record/history caps and tombstones are retained; do not prune them blindly. Offline tasks are plaintext on trusted devices, server encryption is not end-to-end, MFA is absent. Reference: local system-design-primer, consistency/transactions patterns; no code copied.
